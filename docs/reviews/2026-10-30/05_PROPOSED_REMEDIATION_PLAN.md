## 1. مبادئ الخطة

6. **لا ادعاءات:** لا تُعلن مرحلة ناجحة دون تشغيل فعلي موثق.

## 3. Phase 1 — سلامة البيع والمخزون (P0)

### 3.1 الهدف

إصلاح مسار تعديل البيع، وحفظ أثر التعديل/الإلغاء، وضمان تطابق المخزون مع الحركات.

### 3.2 النطاق

**أ. تعديل البيع:**
- استبدال SQL الخام و`SaveChanges` المنفصل بمعاملة EF واحدة (أو معاملة موحدة تشمل كل التغييرات).
- ضمان ذرية: أصناف البيع + الإجماليات + المخزون + الحركات + التدقيق في وحدة عمل واحدة.
- إزالة الاعتماد على أسماء الجداول/الأعمدة النصية.
- معالجة التتبع: إما حذف الأصناف القديمة عبر EF، أو `ExecuteUpdate` داخل نفس المعاملة مع فصل التتبع.

**ب. أثر التعديل:**
- إما كيان `SaleRevision` غير قابل للتغيير، أو حقول تدقيق محفوظة:
  - `Status = Corrected`
  - `ModificationReason`
  - `ModifiedByUserId`
  - `ModifiedAt`
- عدم حذف الحقول التي تحفظ الأثر الأصلي.
- إذا اختير كيان مراجعة، تُحفظ نسخة أصلية كاملة قبل التعديل.

**ج. الإلغاء:**
- حفظ `CancellationReason`، `CancelledByUserId`، `CancelledAt`.
- عدم تجاهل `reason` و`userId`.
- منع الإلغاء المزدوج (موجود) مع رسالة واضحة.

**د. حركات المخزون:**
- إنشاء `StockMovement` لكل منتج تغيّر رصيده في البيع/الإلغاء/التعديل.
- الأنواع: `Sale`، `SaleCancellation`، `SaleCorrection`.
- الحقول: `SaleId`، `QuantityDelta`، `QuantityBefore/After`، `Reason`، `CreatedByUserId`، `CreatedAt`.
- احترام `Store.InventoryEnabled` في الثلاثة.
- إذا كان المخزون معطلًا: لا خصم، لا إرجاع، لا حركة — أو حركة موثقة حسب القرار.

**هـ. الاختبارات المطلوبة:**
- `ModifySale_UpdatesStockByDelta` (تفشل حاليًا) → PASS.
- `ModifySale_ReducingQuantity_ReturnsStock` (تفشل حاليًا) → PASS.
- تعديل يفشل في منتصف العملية → لا تغيير جزئي.
- تعديل مع تعطيل المخزون → لا تغيير مخزون.
- إلغاء بيع مع تعطيل المخزون → لا إرجاع غير مبرر.
- تطابق مجموع الحركات مع الرصيد.
- حفظ سبب/فاعل/وقت التعديل والإلغاء.
- منع تعديل بيع ملغى (موجود) + منع تعديل بيع معدّل حسب السياسة.

### 3.3 معيار القبول

- كل اختبارات Phase 1 خضراء.
- لا `DbUpdateConcurrencyException` في مسار التعديل.
- فحص ثابت: لا SQL خام في `ModifySaleUseCase`.
- عينة بيانات: بيع → تعديل → إلغاء → الأرصدة والحركات والتدقيق متسقة.
- `MVP-AT-11` و`D-20` مستوفيان.

### 3.4 المخاطر

- تغيير المخطط قد يتطلب ترحيل بيانات قائمة.
- كيان المراجعة يضيف تعقيدًا لكنه أنظف قانونيًا.
- تعديل التتبع في EF قد يكسر اختبارات قائمة.

**التخفيف:** ترحيل تدريجي، نسخة احتياطية قبل الترحيل، اختبارات انحدار، ومراجعة كود.

**الجهد التقديري:** M/L.

## 4. Phase 2 — المصادقة والصلاحيات والتدقيق (P0)

### 4.1 الهدف

منع الوصول غير المصرح، وفرض الأدوار، وتوثيق الإجراءات الحساسة.

### 4.2 النطاق

- اعتماد ASP.NET Core Identity أو مصادقة كوكيز مخصصة.
- صفحة تسجيل دخول/خروج.
- `[Authorize]` على الصفحات الحساسة.
- سياسات صلاحيات مبنية على `Permission`/`RolePermissions` الموجودتين.
- إزالة بيانات الدخول الثابتة من `Program.cs`.
- إعداد أول تشغيل آمن (إنشاء أدمن أول بدون كلمة مرور ثابتة).
- ربط `CashierId` بالمستخدم المسجل فعليًا، لا بأول أدمن.
- سجل تدقيق `AuditLog`: من، ماذا، متى، النتيجة، الكيان.
- تدقيق الإجراءات: إدارة المستخدمين، كلمات المرور، النسخ/الاستعادة، مفتاح AI، تعديل الأسعار، تعديل/إلغاء البيع.

### 4.3 معيار القبول

- زائر غير مسجل لا يصل لأي صفحة عمل.
- كاشير لا يصل لإدارة المستخدمين/الإعدادات/النسخ.
- مدير/أدمن حسب المصفوفة.
- كل إجراء حساس له سجل تدقيق.
- لا كلمات مرور ثابتة في الكود أو قاعدة البيانات الافتراضية.
- اختبارات مصفوفة الأدوار + اختبارات رفض الوصول.
- `MVP-AT-10` مستوفى.

### 4.4 المخاطر

- قفل المالك خارج النظام إذا أخطأ إعداد أول تشغيل.
- ترحيل المستخدمين الحاليين.
- تعارض مع بيانات تجريبية.

**التخفيف:** مسار استرداد إداري موثق، اختبار على نسخة، وعدم حذف المستخدمين الحاليين.

**الجهد التقديري:** M.

## 5. Phase 3 — النسخ الاحتياطي والاستعادة (P0)

### 5.1 الهدف

لقطة متسقة، استعادة آمنة، وإثبات فعلي في بيئة منفصلة.

### 5.2 النطاق

- استخدام `SqliteConnection.BackupDatabase` أو `VACUUM INTO` بدل `File.Copy`.
- التحقق من `PRAGMA integrity_check` بعد النسخ وقبل الاستعادة.
- نسخة أمان قبل أي استعادة.
- حذف/عزل `-wal` و`-shm` القديمة قبل/بعد الاستعادة.
- مسار قاعدة بيانات مطلق وموثق.
- التحقق من الإصدار/المخطط قبل الاستعادة.
- سجل نسخة: التاريخ، الحجم، checksum، النتيجة.
- اختبار استعادة في بيئة منفصلة:
  - عينة سجلات.
  - علاقات.
  - أرصدة مخزون.
  - إجماليات بيع.
  - مستخدمون/صلاحيات.
- توثيق إجراء الاستعادة وخطة التراجع.

### 5.3 معيار القبول

- نسخة أثناء كتابة/بيع → تُستعاد سليمة.
- `integrity_check` = `ok`.
- الاستعادة في بيئة منفصلة تنجح مع مطابقة العينات.
- لا فقدان بيانات بعد الاستعادة.
- `MVP-AT-09` مستوفى بدليل مسجل.

### 5.4 المخاطر

- اختلاف إصدار SQLite.
- نسخ احتياطية قديمة غير متوافقة.
- استعادة جزئية.

**التخفيف:** فحص إصدار/مخطط، نسخة أمان، واختبار على بيانات اصطناعية أولًا.

**الجهد التقديري:** M.
